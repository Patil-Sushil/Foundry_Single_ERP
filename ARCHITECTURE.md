# Foundry Project Architecture & Specifications

## 1. Overview
**Foundry** is a modular monolithic ERP platform built for the metal casting industry. While originally designed as a multi-tenant SaaS, the current architecture has been simplified into a **standard monolithic architecture** with a single database schema, focusing on robust core modules for sales, costing, and production.

---

## 2. Tech Stack
- **Language:** Java 21
- **Framework:** Spring Boot 3.2.2
- **Build Tool:** Maven
- **Persistence:** Spring Data JPA (Hibernate 6)
- **Database:** PostgreSQL
- **Migrations:** Flyway
- **Security:** Spring Security + JSON Web Tokens (JWT)
- **Documentation:** SpringDoc OpenAPI (Swagger UI)
- **Utilities:** Lombok, MapStruct, ModelMapper
- **Validation:** Jakarta Validation (Hibernate Validator)

---

## 3. High-Level Architecture
The application follows a standard **Layered Architecture**:
1.  **Controller Layer:** REST endpoints, request/response DTOs, and validation.
2.  **Service Layer:** Business logic and transaction management.
3.  **Repository Layer:** Data access via Spring Data JPA.
4.  **Entity Layer:** Domain models and database mappings.

---

## 4. Authentication & Security
The application uses **Spring Security 6** with **Stateless JWT Authentication**.

### Security Configuration (`SecurityConfig`)
- **Session Policy**: Stateless (no server-side sessions).
- **Public Endpoints**:
    - `/api/auth/**` (Login, Registration)
    - `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html` (Documentation)
- **Filter Chain**:
    - `JwtAuthenticationFilter`: Parses the JWT, validates it, and sets the `Authentication` in the `SecurityContext`. It extracts user identity and authorities from the token.

### JWT Token Structure
Tokens are generated by `JwtTokenProvider` using HMAC-SHA256.
**Standard Claims**:
- `sub`: User email (Subject)
- `iss`: "foundry-erp"
- `iat`: Issued At
- `exp`: Expiration Time

**Custom Claims**:
- `userId`: The UUID of the authenticated user.
- `roles`: List of user roles (e.g., `["ADMIN", "SALES"]`).

### Role-Based Access Control
The system defines several functional roles:
- `ADMIN`: Full system access and user management.
- `SALES`: Handles enquiries and quotation creation.
- `DESIGN`: Technical review and costing analysis.
- `FINANCE`: Financial approval of quotations.
- `PRODUCTION`: Production tracking and planning.

---

## 5. Module Breakdown

### `auth`
Handles authentication, authorization, and user management.
- **Security**: JWT-based stateless authentication.
- **Entities**: `User`, `Role`.
- **Logic**: User registration, login, and bootstrap of default admin.

### `customer`
Manages customer profiles and credit information.
- **Features**: Customer CRUD, credit limit tracking, and status management.

### `enquiry`
Manages sales enquiries from customers.
- **Features**: Enquires with multiple line items, metal category/type associations, and piece weight calculations.

### `quotation`
Comprehensive quotation management system.
- **Features**:
    - Quotation generation from enquiries.
    - Version/Revision tracking.
    - Itemized costing (Metal, Moulding, Melting, Machining, Overheads).
    - Multi-level approval workflow (Pending, Approved, Rejected, Accepted).

### `common`
Shared components and cross-cutting concerns.
- **Audit**: Base entity for tracking `createdAt`, `updatedAt`, `createdBy`, and `updatedBy`.
- **Exceptions**: `GlobalExceptionHandler` providing consistent error structures.
- **Utilities**: Date handling, pagination helpers, and validation logic.

---

## 6. Database Structure
The application uses a single PostgreSQL schema (`public`).

### Key Tables
- `users` & `role`: Security and identity.
- `customer`: Customer master data.
- `enquiry` & `enquiry_item`: Sales enquiry tracking.
- `quotations` & `quotation_items`: Detailed quotation data.
- `quotation_costs`: Granular cost breakdown for quotation items.

---

## 7. API Standards
- **RESTful**: Follows standard REST principles.
- **Response Format**: Unified `ApiResponse<T>` wrapper.
  ``` json
  {
  "success": true,
  "message": "Operation successful",
  "data": { ... },
  "timestamp": "2026-02-17T..."
  }

- **Error Handling**: Consistent error responses with appropriate HTTP status codes (400, 401, 403, 404, 500).

---

## 8. Development & Deployment
- **Profiles**: `dev` (Local development with `DataSeeder`), `prod` (Production environment).
- **Environment Variables**: Sensitive data like `SPRING_DATASOURCE_URL`, `JWT_SECRET`, and `SPRING_DATASOURCE_PASSWORD` are managed via environment variables.
- **Flyway**: Migrations are automatically executed on application startup from `src/main/resources/db/migration`.
